# Three real modules, read end to end

All three live in the public `omni-scrna/split-stages-plan-modules` repository
and serve the `omni-scrna/split-stages-plan` benchmark.

> **Read them for module structure and wrapper logic only.** That benchmark
> declares `api_version: "0.4.0"` and predates `provides`, `requires` and
> `gather`, so its plan-facing metadata is legacy and must not be copied into a
> new plan. For the plan contract the authority is design doc
> `docs/design/004-yaml-specification.md` in `omnibenchmark/omnibenchmark`.
> (Author identifiers in the quoted `pixi.toml` blocks below are replaced with
> placeholders.)
>
> One legacy dependency runs through all three: they build output filenames as
> `<name>_<suffix>` while their plan declares `{dataset}_<suffix>` paths. That
> only lines up because under api ≤ 0.4 the backend passes the dataset as
> `--name`, a workaround the source marks for removal. At 0.7.0 `--name` is the
> module id (spec §3.5); check the stage's `path:` template before copying a
> writer.

## `5-pca-irlba-r` — the minimal shape

```
omnibenchmark.yaml    # entrypoints: {pca: pca.R}
pca.R                 # 92 lines, the whole module
src/cli.R             # 65 lines, the argument parser
check.R               # 11 lines: load every runtime library, print OK
pixi.toml
envs/                 # the exported conda YAML
CITATION.cff  README.md
```

This is the target size for a wrapper. `pca.R` reads the stage's HDF5 matrix,
transposes it, calls `irlba::irlba(Xt, nv = args$n_components, center = col_means)`,
and writes one TSV. The interesting lines are the ones that are not code:

- a header comment naming the algorithm and why this module exists as a
  separate module rather than wrapping the whole upstream framework;
- a comment on *why* centering is passed as `center =` (so the sparse matrix is
  not densified) — an invariant of the wrapper that a reviewer cannot see;
- the parser's own comment: every argument is required, no defaults, so a run
  is reproducible from its invocation line.

`src/cli.R` is separate from `pca.R` only because the sibling modules share the
same shape; a single-entrypoint module can keep the parser inline.

Note one wart to avoid repeating: the parser declares `--normalized_selected.h5`
(a dot) while the plan's stage input id is `normalized_selected_h5` (an
underscore). Generate the parser with `ob create module --for-stage` and the
flag matches the plan by construction.

`pixi.toml`, quoted in full because it is the whole packaging story for a small
R module:

```toml
[workspace]
authors = ["Your Name <you@example.com>"]
channels = ["conda-forge", "bioconda"]
name = "pca-irlba-r"
platforms = ["linux-64"]
version = "0.1.0"

[tasks]
check = "Rscript check.R"
export-env = "pixi workspace export conda-environment --name $(basename $(git rev-parse --show-toplevel)) envs/pca-irlba-r.yml && sed -i '1s/^/# this file was auto-generated by pixi - do not edit by hand\\n/' envs/pca-irlba-r.yml"

[dependencies]
r-base = ">=4.5"
r-irlba = "*"
bioconductor-rhdf5 = "*"
...
```

## `scanpy` — several entrypoints in one repository

```
omnibenchmark.yaml    # eight entrypoints: five scripts + three profiled variants
pca.py knn.py cluster.py normalize.py feat-select.py
prof.sh               # wrapper used by the `*-prof` entrypoints
check.py              # 9 lines: import each runtime package, print OK
src/                  # vendored shared CLI helpers + module-local writers
docs/pca_output.md    # the output contract, in prose
pixi.toml  envs/  .github/workflows/validate-module.yml
```

```yaml
entrypoints:
  pca: pca.py
  pca-prof: prof.sh pca.py
  knn: knn.py
  knn-prof: prof.sh knn.py
  cluster: cluster.py
  cluster-prof: prof.sh cluster.py
  normalize: normalize.py
  feat-select: feat-select.py
```

One file per stage served, each a self-contained script with its own `main()`;
no shared "framework" between them beyond the parser helpers. An entrypoint
value can be a command plus a script, which is how the profiled variants reuse
the same entrypoint file.

`pca.py` is 234 lines and **most of it is a docstring** recording a measurement:
that one advertised solver choice is silently coerced by the upstream library
on sparse input, with the numbers that showed it and three ranked options for
fixing it. That is the right use of length in a wrapper — findings, not
machinery. The executable part is still: parse, load, call, write.

Its parser is worth copying as a pattern (the shared-helper part is house
style; the principle is not):

```python
p = argparse.ArgumentParser(description="PCA module (scanpy-backed)")
cli.add_base_args(p)             # --output_dir, --name
cli.add_stage_args(p, "PCA")     # the stage inputs
p.add_argument("--n_components", type=int, required=True)
p.add_argument("--random_seed", type=int, required=True)
```

The shared contract is injected; the method's own knobs stay hand-written and
visible in the file that uses them. Without the boilerplate, the generated
`ob create module` parser plays the role of the first two lines.

`pixi.toml` is the canonical packaging example (dependencies pinned with both
bounds, a `dev` feature with `no-default-feature = true` so tooling does not
drag in the runtime stack, `test` layering pytest). Detail belongs to the
`omnibenchmark-packaging` skill.

## `metrics` — many stages, two languages, one repository

```
omnibenchmark.yaml        # nine entrypoints: <stage>-py / <stage>-r
annotation/  bounds/  cluster/  embedding/  graph/  integration/
  matrix/  normalization/          # one directory per stage
src/common/cli.{py,R}     # one shared parser engine per language
src/common/schema/*.json  # the stage contracts, vendored from the plan
envs/metrics.yml  pixi.toml
```

```yaml
entrypoints:
  embedding-py: embedding/embedding.py
  embedding-r: embedding/embedding.R
  cluster-r: cluster/cluster.R
  ...
```

The layout to steal: **a directory per stage, an entrypoint file per
language**, and one shared parser that reads the stage contract from JSON so
the Python and R variants cannot drift. `embedding/embedding.py` is 89 lines
including a dict of metric functions — add a metric by adding a dict entry.

Its `pixi.toml` carries Python and R dependencies in one environment (it must:
both languages run from the same exported env), with a comment on every pin
explaining what forced it. That is the standard to hold dependency pins to.

Known defect in this module, not a pattern: its `omnibenchmark.yaml` declares
`templates:` twice (once for R, once for Python), and YAML silently keeps the
second. Whether the vendoring tool was meant to accept a list is unresolved.
