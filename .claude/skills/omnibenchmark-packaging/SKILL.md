# Packaging a module with pixi

Two files, one direction of flow:

```
pixi.toml            <- you edit this. Source of truth for dependencies.
   | pixi run export-env
   v
envs/<name>.yml      <- generated. Never hand-edit. This is what the plan consumes.
```

The benchmark plan's `software_environments` entries point at a conda YAML
(`{name: ..., conda: envs/x.yml}`), and `ob run` hands that YAML to snakemake's
conda backend. Pixi is not in that path at run time — it is the authoring tool
that produces the YAML. So the module gets pixi's solver, task runner and
lockfile while the benchmark keeps a plain conda environment file it can build
anywhere.

Pixi is the recommended route for module environments here. `ob` also supports
an apptainer/docker backend (`software_backend`), which is out of scope for
these skills for now.

## Before you run pixi

Attested commands in the exemplar modules are `pixi install`, `pixi run <task>`,
`pixi run -e <env> <task>`, `pixi run --manifest-path <path> <cmd>` and
`pixi workspace export conda-environment`. For anything else — and for the exact
flags of these — check `pixi <command> --help` against the installed pixi rather
than recalling flags. Pixi renames subcommands between releases
(`[project]` → `[workspace]` is visible across the exemplars themselves).

## 1. A minimal module manifest

The smallest manifest that does the job. This is the whole of the `5-pca-irlba-r`
module's `pixi.toml` (from the public `omni-scrna/split-stages-plan-modules`
repo), with the author line replaced by a placeholder:

```toml
[workspace]
authors = ["Your Name <you@example.com>"]
channels = ["conda-forge", "bioconda"]
name = "pca-irlba-r"
platforms = ["linux-64"]
version = "0.1.0"

[tasks]
check = "Rscript check.R"
export-env = "pixi workspace export conda-environment --name $(basename $(git rev-parse --show-toplevel)) envs/pca-irlba-r.yml && sed -i '1s/^/# this file was auto-generated by pixi - do not edit by hand\\n/' envs/pca-irlba-r.yml"

[dependencies]
r-base = ">=4.5"
r-irlba = "*"
bioconductor-rhdf5 = "*"
bioconductor-delayedarray = "*"
bioconductor-hdf5array = "*"
r-matrix = "*"
r-optparse = "*"
r-data_table = "*"
```

Twenty lines. Start here and add only what the entrypoint actually imports.

To create it on top of an `ob create module` scaffold:

```bash
cd <module>
pixi init                     # writes pixi.toml (check `pixi init --help` for platform flags)
pixi add r-base r-irlba bioconductor-rhdf5   # resolves and records each spec
```

Then add the `export-env` task by hand (below) and run `pixi install` once to
produce `pixi.lock`. Ten of the thirteen exemplar module manifests commit
`pixi.lock`; commit yours — it is what makes a re-solve on another machine
reproducible even though the exported YAML is not (see §3).

**Core `ob` vs house style.** Nothing about pixi is core `ob`. `ob` only cares
that `software_environments.<env>.conda` names a readable conda YAML. The
`export-env` task, the `envs/<name>.yml` location and the banner are
`omni-scrna` conventions — good ones, and adopted here, but say so when you
explain them to an author outside this lab.

## 2. The `export-env` task, piece by piece

Eleven of the thirteen exemplar manifests carry this task, character-identical
apart from the filename. Teach it rather than pasting it silently:

```bash
pixi workspace export conda-environment --name $(basename $(git rev-parse --show-toplevel)) envs/<name>.yml
```

| piece | what it does | when you change it |
| --- | --- | --- |
| `workspace export conda-environment` | renders the default environment as a conda YAML | never |
| `--name $(basename $(git rev-parse --show-toplevel))` | sets the `name:` field in the YAML to the repo directory name | if the env name must differ from the repo name — then hard-code it, don't drop the flag |
| `envs/<name>.yml` | output path, the positional argument | matches the path the plan's `software_environments` entry names |

The `&& sed -i '1s/^/# this file was auto-generated by pixi - do not edit by hand\n/'` half
stamps the banner on line 1. It exists because the exported file looks editable
and is not: the next `pixi run export-env` overwrites it.

Run it whenever `[dependencies]` or `[pypi-dependencies]` changes, and commit
both `pixi.toml` and the regenerated `envs/<name>.yml` in the same commit:

```bash
pixi run export-env
git add pixi.toml pixi.lock envs/<name>.yml
```

## 3. What the export actually contains — and does not

The export writes **the manifest's version specs, not the locked versions**. The
scanpy module's `pixi.toml` says `python = ">=3.14.4,<3.15"` and its
`envs/scanpy.yml` says `- python >=3.14.4,<3.15`. Consequences, in order of how
often they bite:

- The exported YAML is a *constraint file*, not a lockfile. Conda re-solves it at
  `ob run` time, so two runs weeks apart can use different builds.
- Loose specs export loosely. `r-matrix = "*"` becomes `- r-matrix *`.
- `channels` are exported in manifest order with `nodefaults` appended.

If a run must be bit-reproducible, `pixi workspace export conda-environment` can
render the resolved versions instead of the manifest specs:

```bash
pixi workspace export conda-environment --from-lock-file --name <env> envs/<name>.yml
```

`--from-lock-file` pins every package to the version `pixi.lock` resolved, producing
a frozen environment file. Two further flags on the same command are worth knowing:
`--no-pypi` omits the `pip:` section entirely, and `-p/--platform` renders for a
platform other than the current one — useful when the benchmark runs on `linux-64`
and you are authoring on a Mac.

None of the exemplar modules use `--from-lock-file` today; they all export manifest
specs. Raise it with the author as a deliberate choice rather than switching an
existing module over unilaterally — a frozen export changes what `ob run` solves, and
the plan-side copy would have to be regenerated to match.

## 4. PyPI dependencies become a `pip:` block

A `[pypi-dependencies]` entry surfaces in the export under `pip:`, and pixi adds
a bare `pip` conda dependency alongside it. From the scanpy module:

```toml
[pypi-dependencies]
obkit = ">=0.0.3, <0.0.4"
```

exports as

```yaml
- pip
- pip:
  - obkit>=0.0.3, <0.0.4
```

Extras and exact pins survive the round trip: the rapids module's
`rapids-singlecell-cu13 = { version = "==0.16.1", extras = ["rapids"] }` exports
as `- rapids-singlecell-cu13[rapids]==0.16.1`.

Use `[pypi-dependencies]` only when the package is genuinely not on
conda-forge/bioconda, and say why in a comment — the `metrics` module does
exactly that for `scib-metrics`. A mixed conda+pip environment is harder to
solve and harder to reproduce, so it is a cost you take deliberately.

## 5. The `dev` feature: tooling that must not pollute the runtime

Five of the thirteen manifests add a feature for bootstrap/dev tooling and
isolate it with `no-default-feature = true`:

```toml
[feature.dev.dependencies]
python = ">=3.11"
pyyaml = ">=6"
curl = "*"

[feature.dev.tasks]
sync = "sh -c 'curl -fsSL https://raw.githubusercontent.com/omni-scrna/boilerplate/${BRANCH:-main}/scripts/pull.py | python -'"

[environments]
dev = { features = ["dev"], no-default-feature = true }
```

`no-default-feature = true` means the `dev` environment contains *only* the dev
feature — not the module's runtime stack. That is the point: on an R module or a
GPU module, solving the heavy runtime just to run a Python sync script costs
minutes and can fail for reasons unrelated to the task. Run it with
`pixi run -e dev sync`.

Contrast with a **test** feature, which usually *does* want the runtime, so it
layers instead:

```toml
[feature.test.dependencies]
pytest = ">=8"

[environments]
test = { features = ["test"] }        # no no-default-feature: default deps included
```

Rule of thumb: tooling that does not import the module's code →
`no-default-feature = true`. Tests that import the module's code → layer.

(The `sync` task above vendors `src/common/` from the `omni-scrna/boilerplate`
repo. That is lab-specific infrastructure, not part of `ob`.)

## 6. The `check` task — where a module's invariants live

Nine of the thirteen manifests define `check`, and it is the cheapest thing in
the module:

```toml
check = "python check.py"    # or: Rscript check.R
```

The exemplar `check.py` files are an import list and `print("OK")` — they answer
"did the environment solve into something the entrypoint can actually run", and
catch the common failure where a dependency was added to the code but not to
`pixi.toml`.

That is the floor, not the ceiling. `check` is also the natural home for the
**stage-contract invariants** the module promises: output file exists and is
non-empty, row count equals the input's cell count, column count equals
`--n_components`, cell identifiers survive the transform. The `rcppml` module
puts a version gate in `check.R` (`RcppML >= 1.0.0`, with an error message
naming the channel that provides it) because a silently-older package would
produce wrong results rather than a crash.

Write the invariant down the moment you rely on it, and prefer a one-line
`assert` / `stopifnot` next to the code it guards over a test file elsewhere.
An assertion encoding something a reviewer cannot check by eye is documentation;
a test asserting a function returns what it just returned is noise.

Add the dependency and its check in the same small commit. One dependency
bumped, exported, checked and committed is reviewable; a branch that rewrites
the whole manifest is not.

## 7. Bumping a dependency

```bash
pixi add "scanpy>=1.12.1,<2"   # or edit pixi.toml and re-solve
pixi install                   # re-solve, update pixi.lock
pixi run check                 # imports still work?
pixi run export-env            # regenerate envs/<name>.yml
git add pixi.toml pixi.lock envs/<name>.yml
```

Then run the module's entrypoint once against a real sample input before you
push — a solve that succeeds is not the same as a module that still runs.

If the solve fails, read the conflict rather than loosening every bound. The
exemplars show the two useful fixes, both recorded as comments in the manifest:

- **Cap the offending package and say why.** The `metrics` module pins
  `python = ">=3.12,<3.14"` and `numpy = "<2.5"` with a comment naming numba
  (via `scib-metrics` → `pynndescent`/`umap-learn`) as the reason. When the
  upstream constraint lifts, the comment tells you which pin to retry.
- **Add the channel that has the version you need, ahead of the others.** The
  `rcppml` module lists `"https://prefix.dev/almost-conductor"` first because
  conda-forge stops at `r-rcppml 0.3.7.1`, which predates the functions the
  module calls. Channel order in `[workspace].channels` is precedence order.

Never edit `envs/<name>.yml` to fix a solve. That file is downstream; the fix
belongs in `pixi.toml`.

## 8. Harmonising a new module against the existing ones

Two different questions hide here — keep them apart.

**One environment per module.** Modules do not co-solve. The scanpy arm and the
scvi arm are separate conda environments, so scanpy's `numpy >=2.4.3,<3` and
scvi's `numpy >=2.5,<3` coexist happily, and the `metrics` module's
`numpy <2.5` conflicts with neither. You are not obliged to match your
neighbours' pins.

**Comparability across arms.** You often *should* match them anyway, because a
benchmark comparing two implementations of one method should not accidentally be
comparing two versions of the shared I/O stack. The exemplars do this explicitly:
the rapids module pins `polars >=1,<2` with the comment "Same pin as the scanpy
module: the TSV writers are the same code in both, so they must be the same
polars", and the scvi module pins `obkit` "same pin as the rapids module".

So the rule is: **anything that touches the benchmark's shared file formats or
instrumentation should carry the same constraint as the sibling modules; the
method's own stack is free.** For the surveyed constraint table — every
dependency used by two or more of the thirteen exemplar modules, with the spec
each one uses — see `references/harmonising.md`. Check your new module against
it before you invent a pin, and when you deviate, comment why in the manifest.

When one env is genuinely shared by several modules (the plan's `scanpy` and
`scrapper` environments each serve multiple entrypoints), the constraints
*do* have to co-solve, and a bump there is a change to every arm that uses it.
Say that out loud in the PR.

## 9. Getting the exported YAML into the plan

The plan repo holds its own copy under its `envs/` directory — the path in
`software_environments.<env>.conda` is relative to the plan, not to the module.
Copying the module's export across is a manual step today, and in
`omni-scrna/split-stages-plan` the two sides have drifted: the plan's
`envs/scanpy.yml` carries the auto-generated banner yet has a different
`python-igraph` bound, an extra channel and `obkit` moved out of the `pip:`
block, none of which is in the module's export. Six of the plan's eighteen env
files carry the pixi banner at all; the rest were written by hand.

So: when you change a module's environment, say explicitly that the plan-side
copy needs updating too, and diff the two before assuming they agree.

```bash
diff -u <module>/envs/<name>.yml <plan>/envs/<name>.yml
```

A banner that says "do not edit by hand" on a file somebody has edited by hand
is worse than no banner. If a plan-side edit is genuinely needed, it belongs in
the module's `pixi.toml` and a re-export.
